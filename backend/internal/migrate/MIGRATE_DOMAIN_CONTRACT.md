# Clario Migrate Domain Contract

Clario Migrate owns cloud-migration orchestration for tenant programs. It does not
replace Recover/DR inventory or runbook systems; it links to them by stable IDs
and uses their data where available.

## Tenant Scope

Every persisted table includes `tenant_id`. Migrations enable and force row-level
security on all Migrate tables. Runtime database work must execute through the
tenant runner so `app.tenant_id` is set before reads/writes.

## Core Entities

- `migrate_program`: migration portfolio container and reference sequence root.
- `migrate_workload`: application/workload inventory imported from CSV or entered
  through the UI, optionally enriched from Recover Metastore by `app_key`.
- `migrate_move_group`: dependency-complete migration grouping. Workloads can be
  assigned to one group.
- `migrate_wave`: sequenced migration wave containing approved move groups.
- `migrate_cutover_window`: governed execution window with overlap checks.
- `migrate_rollback_plan`: one rollback plan per cutover window.
- `migrate_gate_check`: readiness, validation, and rollback-success gates.
- `migrate_connector_config`: tenant-owned HTTP connector configuration.
- `migrate_connector_invocation`: idempotent connector execution record.
- `migrate_audit_event`: append-only evidence stream.

## State Rules

Workload transitions are defined by `WorkloadTransitionTable`.

Wave transitions are defined by `WaveTransitionTable`.

Move groups must be validated before submission. A submitted move group must be
approved before it can be assigned to a wave.

Cutover start requires:

- cutover window decision is `go`;
- rollback plan exists and is `approved`;
- all required readiness checks are `passed` or `overridden`.

Cutover completion requires all required validation checks are `passed` or
`overridden`.

## Evidence

Migrate evidence is exported from persisted audit rows only. CSV and PDF exports
are generated by `EvidenceService`; the audit table is protected by an append-only
database trigger.

## Connector Contract

Connectors make real HTTP POST calls to configured endpoints. Secrets are resolved
from environment variables referenced by `secret_ref` and are never returned in
API responses. Invocations require an idempotency key and are persisted before
execution.
